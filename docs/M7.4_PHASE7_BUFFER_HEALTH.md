# M7.4 Phase 7 — PSRDADA buffer health → Grafana

Status: **wired and tested**. The fleet picks this up automatically on
the next sync + relaunch — no operational change required.

## Root cause (gate-soak finding)

The 30-min gate soak rolled up cluster snapshots showing
`buffers.<k>.metric == {}` on every corr node despite the rings being
healthy and the `dada_dbmetric` binary present at
`/usr/local/bin/dada_dbmetric`:

```text
3 running    2030s     ... | {'key': 'dada', 'metric': {}}/{'key': 'eada', 'metric': {}}/...
```

Sub-agent inventory ([details](M7.4_PHASE_PLAN.md#post-gate-phases-5-9))
showed `_dada_dbmetric()` in `src/dsart/services/dsart_rt.py` already
calls the binary every 2 s from `_publish_mon_dict`, and the Influx
pusher already maps non-empty `metric` to a `corr_rt_buffer`
measurement. So why did the dict stay empty?

The cluster's `/usr/local/bin/dada_dbmetric` (built Jun 26 2025) writes
the metric line to **STDERR**, not STDOUT. The existing parser only
consumed `proc.stdout`. Manual verification on h23:

```bash
$ dada_dbmetric -k dada >stdout.txt 2>stderr.txt
$ cat stdout.txt     # empty
$ cat stderr.txt     # "4,0,3,9,9,4,0,3,3,3"
```

## Fix (`src/dsart/services/dsart_rt.py`)

`_dada_dbmetric()` now:

1. **Coalesces stdout + stderr** before parsing (filtering only the
   well-known `ipc_alloc / ipcsync_get / ipcbuf_connect` 3-line chain
   that fires when a ring doesn't exist).
2. **Falls back to the absolute path** `/usr/local/bin/dada_dbmetric`
   if the bare name isn't on PATH (covers systemd-style minimal-env
   launches).
3. **Maps the legacy 5-column CSV** to canonical field names via the
   module-level `_DBMETRIC_CSV_FIELDS = ("nbufs", "nfull", "nclear",
   "n_written", "n_read")`. The CSV-to-name map is the same one the
   legacy correlator's `corr.py::get_buf_info()` uses.
4. **Adds derived fields** via `_normalise_dbmetric()`:
   `free_blocks = nbufs - nfull`, plus `free` / `full` aliases so the
   legacy snapshot scripts (`_m72_snapshot.py`) keep working.
5. **Surfaces failures as `_error: <reason>`** instead of `{}`, so an
   operator querying `/mon/corr_rt/<cn>` can see *why* a buffer is
   dark (missing binary, transient race, typoed key, etc.). The Influx
   pusher skips `_error`-only dicts (no numeric fields ⇒ no series),
   so Grafana stays clean.

Live verification on h23 (with a small 4-block ring present):

```python
>>> _dada_dbmetric("dada")
{
  "nbufs": 4, "nfull": 0, "nclear": 3,
  "n_written": 9, "n_read": 9,
  "raw_csv": "4,0,3,9,9,4,0,3,3,3",
  "free_blocks": 4, "free": 4, "full": 0
}
```

## Grafana (`tools/dashboard/dsart_rt_to_influx/grafana/build_dashboard.py`)

Five new panels in the `dsartRtMpV1` dashboard on h20:

1. **PSRDADA fill fraction — fleet mean per buffer** (replaces the
   orphan `n_blocks_free` capture-ring panel that queried a field the
   pusher never wrote).
   `nfull / nbufs` over the 4 buffer names; percentunit y-axis 0–1.
2. **PSRDADA nfull per (cn, buffer) — fada (corr→search merge)**.
   `last("nfull")` filtered to `buffer = 'fada'`. fada has nbufs=70;
   alarm threshold ≥ 50.
3. **PSRDADA nfull per (cn, buffer) — dada / eada (SNAP capture)**.
   Same shape for the capture rings (nbufs=20 each); alarm threshold
   ≥ 18.
4. **PSRDADA free_blocks per (cn, buffer) — fleet view**. The
   complement; the operationally-useful number.
5. **PSRDADA n_written rate (blocks/s) per (cn, buffer)**. Derivative
   of the cumulative `n_written` counter — should track ~9.6 blocks/s
   on dada/eada and ~7.45 blocks/s on fada at the M7.4 op-point.

Total dashboard panel count: **17 → 22**.

Regenerate + POST to live Grafana:


  `fada.nfull >= 50` (or `free_blocks <= 20`) to catch search-side
  drops *before* they manifest as `kernel_drops_total > 0`.

  report): comparing n13's `fada.nfull` history vs the other 3
  search-feeding corr nodes should isolate whether the noise is
