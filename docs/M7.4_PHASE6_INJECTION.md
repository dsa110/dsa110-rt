## Hook (Phase 6b) — production wire-in

The injector is invoked **after `unpack_int4_split`** and **before
the RFI flagger** in
[`_process_block_corr_phase`](../src/dsart/services/corr_fast_integration.py).
That insertion point exercises the full downstream chain
(RFI → cal → GEMM → grid → coarse-DM → static-sky → transport →
search) on injected pulses, so recovery tests measure the same
pipeline that real bursts travel.

```text
fada raw bytes
   │
   ▼ unpack_int4_split
voltages_real / voltages_imag (GEMM layout)
   │
   ▼ ★ ctx.injector.apply_block(real_v, imag_v, block_specnum_start)  ← Phase 6 hook
   │
   ▼ RFI flag → voltage zero-fill
   ▼ apply_cal_split (F21 DEC-phase fold)
   ▼ FastCorrKernel.compute_split (Stokes I)
   ▼ Stage-1 multi-DM coarse dedisp + gridder
   ▼ StaticSkyEMA
   ▼ TransportTX → search
```

### Surface

#### `FastIntegrationConfig.inject_configs: tuple[InjectionConfig, ...]`

Default `()`. When non-empty, `build_context` constructs an
`OnlineInjector` for the chgroup with the loaded antpos and queues
each config via `add_pending`. The injector is reused for the
lifetime of the service.

#### `IntegrationContext.injector: OnlineInjector | None`

Default `None`. When `None`, the hot path has zero overhead (one
`is None` test per block).

#### CLI: `--inject-spec <JSON>` (repeatable)

Pass a JSON dict matching
`InjectionConfig.to_json()`. Repeat for multiple simultaneous
injections.

```bash
python -m dsart.services.corr_fast_integration \
    --fada-key fada --device cuda:0 --chgroup 0 \
    --obs-dec-deg 53.85 --apply-cal /path/to/cal.dat \
    --dm-plan-path /home/ubuntu/proj/dsart/configs/dm_plan_N8_dmmin100_tol1.6_v2.npz \
    --chan-sum-factor 8 --t-int-fast-native 8 \
    --inject-spec '{"inj_id":"phase6_extragal","l_rad":0.0,"m_rad":0.0,
                    "dm_pc_cm3":500.0,"fluence_jy_ms":50.0,
                    "width_samples":32,"profile":"gaussian",
                    "apply_at_specnum":20480}' \
    --inject-spec '{"inj_id":"phase6_galactic","l_rad":0.02,"m_rad":0.01,
                    "dm_pc_cm3":20.0,"fluence_jy_ms":100.0,
                    "width_samples":64,"profile":"gaussian",
                    "apply_at_specnum":40960}'
```

`apply_at_specnum` is referenced to **service start**: one block =
2048 specnums = 4096 native samples, so an injection at
`apply_at_specnum=20480` fires at block-counter `n = 10`. Allow a
few blocks of orchestrator/Triton-JIT warmup before the first
target.

### Sign + dispersion conventions

- Phasor: `exp(+2πi · ν_ch · (E_a·l + N_a·m + U_a·n)/c)` (POSITIVE
  sign — DSA-110 SNAP voltage convention; pinned by
  `test_F22_visibility_phase_matches_lm_target`).
- Dispersion: cold-plasma law referenced to `NU_TOP_PROC_GHZ`
  (peak at the top-of-band channel arrives at
  `apply_at_specnum * 2` native samples; lower channels delayed
  by `K_DM · DM · (ν_ch⁻² − ν_top⁻²)` ms).
- Intrinsic profile: `gaussian` (unit-area over
  ±`MAX_WIDTH_SAMPLES`) or `boxcar` (unit-area, divide by width).
  Peak amplitude scale `√(fluence_jy_ms / width_samples)`.

## Phase 6 runtime (added 2026-05-28)

The original Phase 6b wired startup-only injection. To support the
operator workflow ("queue an injection while the fleet is live"),
this session added three pieces:

### 1. `RuntimeInjectWatch` in
[`src/dsart/inject/runtime_watch.py`](../src/dsart/inject/runtime_watch.py)

DsaStore-based watcher that listens on
``/cmd/dsart/corr/<chgroup>/inject``. Each PUT is dispatched into
``OnlineInjector.add_pending`` via the shared
:func:`dsart.inject.etcd_watcher.handle_inject_payload` parser
(single source of truth for the wire schema). Malformed payloads
are logged at WARNING and dropped — the watch thread never raises
into the service. Counters: ``n_events`` (raw PUTs received),
``n_queued`` (successful ``add_pending`` calls).

### 2. `--inject-watch` flag in `corr_fast_integration`

Wired in two places:

* `FastIntegrationConfig.inject_watch_enabled: bool` (default
  ``False``). When ``True``, ``build_context`` *always* builds an
  ``OnlineInjector`` even if the startup CLI ``--inject-spec``
  queue is empty (the watch needs a live injector to feed).
* `run()` opens a ``RuntimeInjectWatch`` after ``build_context``
  and ``stop()``s it in the ``finally`` block. The watch survives
  service signals and broken etcd connections (DsaStore handles
  the reconnect).

```bash
# How the Phase B launch script should call it once we go
# routine-attended again:
python -u -m dsart.services.corr_fast_integration \
    --fada-key fada --chgroup 0 --obs-dec-deg 53.85 \
    --apply-cal ... --inject-watch \
    ... (rest of the production args)
```

The flag is harmless when no operator pushes inject payloads — it
just costs one DsaStore watch handle. Safe to leave on in the
production config.

### 3. Control-tab "Send injection" panel

`dsa_monitor` exposes a form with the 8 `InjectionConfig` fields +
a comma-separated chgroups subset + an auto-arm checkbox (blank
``apply_at_specnum`` ⇒ `compute_arm_seq(margin) + max(last_seq_no)`
of the live captures). Flask route ``POST /control/inject``
validates the payload via the dashboard's torch-free
``_validate_inject_payload`` (mirrors
``InjectionConfig.__post_init__``), broadcasts ``{cmd: "inject",
val: <cfg>}`` to each requested ``/cmd/dsart/corr/<chgroup>/inject``
key via ``control_store.send_inject``, and writes one summary
audit row to ``/mon/audit/control/<iso-ts>``.

The torch-free validation is deliberate — the h23 dashboard env
does not have torch / numpy / cuda; we mirror
``InjectionConfig.__post_init__`` exactly. Drift between the two
validators is caught by
``tests/test_dsa_monitor_control_store.py::TestSendInject`` and
``tests/test_runtime_inject_watch.py``.

## E2E findings (2026-05-28 unattended soak)

The first attempt at a live on-fleet E2E with ``--inject-watch`` and
five operator-side ``control_inject_pulse`` invocations surfaced **two
bugs** that gate the Phase 6c recovery benchmark.

### Bug 1 — apply_at_specnum epoch mismatch (open)

``control_inject_pulse`` derives ``apply_at_specnum`` from
``compute_arm_seq`` (= ``max(/mon/corr_rt/<cn>/capture/<port>.last_seq_no)
+ margin``). That ``last_seq_no`` is the **SNAP packet sequence number**
(SNAP-header epoch, currently ~1.95 × 10¹⁰).

The ``corr_fast_integration`` hot path passes
``block_n × NPACKETS_PER_BLOCK`` to ``OnlineInjector.apply_block`` —
that is the **service-start block counter epoch** (current ~1.5 × 10⁷
after ~17 min of processing).

The two epochs differ by three orders of magnitude.  Result: the etcd
watch fires, ``OnlineInjector.add_pending`` accepts the payload, and
``handle_inject_payload`` logs *“inject queued: id=…”*, but
``apply_block`` never observes ``footprint_first < block_native_end``
because ``apply_at_specnum`` is several years' worth of blocks in the
future.  No ``M7.4 inject:`` hot-path log line ever appears.

Workaround (this session): a ``send_manual_inject.py`` helper script
that ssh's n03, reads the live ``processed n_in=N`` from the corr_fast
log, and writes ``apply_at_specnum = (n_in + 15) × 2048`` directly to
``/cmd/dsart/corr/<cg>/inject``.  This consistently produces the
expected hot-path log line, e.g. (verified on n03):

```
M7.4 inject: block_n=7507 specnum_start=15374336 active=['m74e2e_manual_dm300'] n_purged=0
M7.4 inject: block_n=7508 specnum_start=15376384 active=['m74e2e_manual_dm300'] n_purged=0
M7.4 inject: block_n=7509 specnum_start=15378432 active=['m74e2e_manual_dm300'] n_purged=0
```

…and the C2 receiver picked up the downstream candidate: ``accepted``
incremented (96→97) and ``triggers_dump`` went from 25 → 27, with the
new event ``260528wdxt`` classified as ``bright_pulsar``.

The proper fix is one of:
* Have ``corr_fast`` publish ``block_n`` (or the equivalent
  service-start specnum) to ``/mon/corr_rt/<cn>/corr_fast`` and have
  ``compute_arm_seq`` for ``inject`` (vs ``utc_start``) source from
  that key.
* Or have the corr_fast hot path source ``block_specnum_start`` from
  the SNAP packet header rather than the service-start block counter
  (= the M7.2.8 corner-turn work already on the milestone list).

Either way, the temporary unblock is the
``tools/ops/_inject_helper_apply_at.py`` (drop-in for the helper
script that ran in the soak) — but the Control-tab "Send injection"
button is **broken** until this is fixed.

### Bug 2 — dict-iteration race in OnlineInjector.apply_block (fixed)

Symptom: 11 s after the first successful injection the corr_fast log
showed:

```
File "/home/ubuntu/proj/dsa110-rt/src/dsart/inject/online.py", line 783, in apply_block
    for inj_id, active in self.pending.items():
RuntimeError: dictionary changed size during iteration
```

Root cause: ``OnlineInjector.apply_block`` (main thread) iterates
``self.pending.items()`` while ``RuntimeInjectWatch._on_event`` (DsaStore
watch thread) can call ``add_pending`` which writes to the same dict.
CPython's dict iterator raises on size change.

Fix: snapshot ``list(self.pending.items())`` before the loop.  The
snapshot may miss a brand-new injection added by the watch during the
current block; it is picked up on the next ``apply_block`` (~125 ms
later).  The fix is one line — see commit on or near this
edit — and was deployed live to all 16 corr nodes during the soak;
post-fix stress test (two back-to-back PUTs to all 16 chgroups)
showed 16/16 corr_fast survival.
