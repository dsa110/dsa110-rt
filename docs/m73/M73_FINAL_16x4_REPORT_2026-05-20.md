# M7.3 Final Report — 16x4 Production Soak (2026-05-20)

**Status: M7.3 DONE.** The full 16x4 fleet (16 corr + 4 search nodes,
2 coarse DMs per search node) sustained the **7.45 cubes/s production
real-time target** over a 55-minute steady-state window, with zero
corr-side TX drops and search-side ingress fully tracking the corr
output. This run validates the post-M7.4-plumbing redeploy: the
ring-v2 wire layout (per-slot `scale`/`offset` sidecars) is healthy
end-to-end on production traffic.

## What changed vs. the previous (M7.3 baseline) run

This is a **fresh restart** of the 16x4 fleet after:

1. **`RX_RING_VERSION` bump 1 → 2.** Per-slot wire layout grew the
   `scale` + `offset` `float32` sidecars (8 B per slot; ~0.16% larger
   ring footprint) so the search-side has the per-(corr, dm, t) calib
   metadata available for the M7.4 dense-scatter path. All 4 search
   nodes attached cleanly to the v2 rings; no version-mismatch
   warnings.
2. **`rx_ring_assemble_dense_block`** C helper deployed to all 20
   nodes. The Python bindings + `ProductionRxRingSource` opt-in path
   are present but **the LUT is not yet wired into `search_compute.py`**,
   so this run continues to use the M7.2 zero-stub validity path. The
   M7.4 scatter is dormant scaffolding pending the LUT-build step
   (next milestone).
3. **`recv_epoll.c` updated** to extract `scale`/`offset` from the
   `prod_hdr_t` and pass them through to `rx_ring_write_slot`. Zero-fill
   slots are written with `(0.0, 0.0)`, which the new helper interprets
   as "no contribution" downstream.

Net effect on this run: identical search-side compute path as the
previous M7.3 baseline, but on the ring-v2 wire format. The fact that
the steady-state rate is unchanged at `7.45 cubes/s` confirms the
ring layout change is performance-neutral, as designed.

A pure-C smoke test (`tools/ops/_m74_smoke_dense_block.py`) plus a
pytest suite (`tests/transport/test_recv_ring_assemble_dense.py`) for
the new scatter helper are now in main; both pass locally and on every
fleet node post-`_sync_fleet.sh` rebuild.

## Limits / known gaps

* **M7.4 scatter is plumbing-only on this run.** The dense-scatter
  path is wired end-to-end (C helper + GPU per-t kernel + CubeRingSlot
  fields) but inactive in this run because the per-corr linear LUT is
  not yet built on the search side. Activating it requires loading the
  same antpos + sparsity-pattern inputs the corr side uses, then
  passing `(linear_lut_per_corr, owned_coarse_dm, n_filled_per_corr)`
  into `ProductionRxRingSource`. This is a separate milestone (M7.5
  imager-data-path activation).
* **DM-plan tolerance tuning is committed but not yet runtime-toggleable.**
  `tools/build_dm_plan.py` now exposes `--chan-sum-factor` (default 8)
  and `--tol-coarse-seed`; the chan-summed fine recursion is the
  physically correct form (Δν = 0.244140625 MHz, N_chan = 768). A
  runtime DM-tol parameter is on the M7.5 list.
* **Slow correlator output path** (`bada` ring → drain) is healthy in
  this run; the in-tree `dsart.services.dada_drain` consumer keeps the
  back-pressure chain unblocked. No slow-correlator analysis consumer
  is wired into the M7.3 stage; that path is decoupled by design and
  drains to `/dev/null` for the purposes of this RT validation.
