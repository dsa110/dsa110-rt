## What we did NOT do (and why)

**`meridian_fringestop` was NOT started during this E2E.** The
`dsa110-meridian-fs` package's canonical `dsa_parameters.yaml` ships
with a `ch0` host-map keyed by `corr00`–`corr16` (legacy hostnames),
while the M7 fleet uses `lxd110h03`–`lxd110h22`. In the running code
(`dsamfs/utils.py:371-378`) the `gethostname()` lookup falls through to
`KeyError` → silent fallback to `ch0 = 3400, subband = 0`, which means
**all 16 nodes would silently write UVH5 files tagged with the WRONG
frequency offset**. The fix (write a dsart-shipped `dsa_parameters_phaseB.yaml`
keyed on `lxd110h*` and verify it on one node before fleet rollout)
is out of scope for an unattended session — see
`docs/M7.4_PHASE_PLAN.md` Phase 9 inventory. Phase 9 stays in its
existing **INVENTORY DONE / reintegration DEFERRED** state until an
operator-attended next session.

## Bug catalog

### Bug 1 — `apply_at_specnum` epoch mismatch (open)

`control_inject_pulse` → `compute_arm_seq` returns the SNAP-header
specnum from `/mon/corr_rt/<cn>/capture/<port>.last_seq_no` (currently
~1.95 × 10¹⁰). The corr_fast hot path calls
`OnlineInjector.apply_block(block_specnum_start=int(block_n) *
NPACKETS_PER_BLOCK)` where `block_n` is the service-start block
counter (currently ~7 500 after 17 min of processing × 2048 ≈
1.5 × 10⁷).

The two epochs differ by three orders of magnitude. Result: the etcd
watch fires, `add_pending` accepts the payload, `inject queued: id=…`
logs cleanly, but `apply_block`'s `footprint_first < block_native_end`
test never passes — the injection lives forever in `self.pending` (or
gets auto-purged once `block_n × 2048 > apply_at_specnum + width` which
is decades away).

**Workaround used in this session:** `/tmp/send_manual_inject.py`
sshs to n03, parses `processed n_in=N` from the corr_fast log, picks
`apply_at_specnum = (n_in + 15) × 2048`, and writes 16 PUTs directly
to `/cmd/dsart/corr/<cg>/inject`. Verified hot-path-correct.

**Proper fix (Phase 6c):** publish `block_n` (or its equivalent
service-start specnum) to `/mon/corr_rt/<cn>/corr_fast` and route the
inject path of `compute_arm_seq` through that key. Alternatively,
make corr_fast pull `block_specnum_start` from the SNAP packet header
itself — that is the M7.2.8 corner-turn work already on the milestone
list. Either fix unblocks the Control-tab "Send injection" button,
which is currently **non-functional** even though all the etcd / Flask
plumbing works.

### Bug 2 — `OnlineInjector.apply_block` dict iteration race (fixed)

**Symptom:**

```
File "…/dsart/inject/online.py", line 783, in apply_block
    for inj_id, active in self.pending.items():
RuntimeError: dictionary changed size during iteration
```

**Root cause:** `apply_block` iterates `self.pending.items()` from the
corr_fast main thread; `RuntimeInjectWatch._on_event` (DsaStore watch
thread) writes to `self.pending` via `add_pending`. CPython raises if
the dict resizes during iteration.

**Fix (one line):** snapshot to a list before iteration:

```startLine:783:src/dsart/inject/online.py
        for inj_id, active in list(self.pending.items()):
```

The snapshot may miss a brand-new injection added during the current
block; it will be picked up on the next `apply_block` call — at most
one block (~125 ms) of additional latency. The other end of the
critical section (`del self.pending[inj_id]` for purged ids) only
mutates the entries the snapshot already pinned, so it's safe with or
without the snapshot.

**Verification:** post-fix, fired 3 injections within 8 s (DM 300 +
DM 600 + DM 900) and 2 more 50 s later (DM 400 + DM 200). All 16
corr_fast instances stayed alive through the burst. 5 of 7
injections produced hot-path `M7.4 inject: block_n=N
specnum_start=X active=['<id>']` log lines (the other 2 — DM 500 and
DM 300 from the first burst — were both "target block already past"
purges, which is the correct behavior).

## 2026-05-28 follow-up: Bug 3 + Bug 4 fixed

Two new bugs surfaced during the post-fix soak ahead of the
fluence-calibration sweep, and have now been fixed (this branch,
post-`452fc23`).

### Bug 3: `cube_dump_now` synthetic trigger used the wrong specnum domain

**Symptom.** Operator clicks "Dump Now" on the Control tab. The
Flask layer broadcasts the synthetic `C2TriggerPacket` to every
search-half. Search nodes log `C2TriggerListener miss (too_early)`
for every datagram, and no cube is ever staged for upload.

**Root cause.** The first cube_dump_now subagent picked the target
`event_specnum` from the *corr_fast* mon-key
(`/mon/corr_rt/<cn>/corr_fast`'s `block_specnum_start =
block_n × NPACKETS_PER_BLOCK`). That counter is **service-start
relative** — at 17 min of uptime it's ~1.5 × 10⁷. The search-side
`CubeRetentionRing`, however, keys cubes by `slot.specnum_start`,
which is the **SNAP-header** specnum coming through the capture
chain (~10¹⁰ after months of uptime). Three orders of magnitude
apart → every synthetic trigger lands "before" the first ring
slot.

**Fix.** Introduce a *second* mon-key publisher,
`dsart.services.search_ring_mon.SearchRingMonPublisher`, that
publishes the ring window to `/mon/search/<sid>/<gpu_half>/ring`
once per `cube_progress` log cycle (≈ 1.3 s at 7.45 cubes/s). The
payload exposes:

* `newest_event_specnum_start` / `newest_event_specnum_end`
* `oldest_event_specnum_start`
* `n_committed`, `depth`, `t_det`, `n_fdm`, `n_grid`,
  `sample_period_specnum`
* `ts_mono` / `ts_wall_unix` for freshness gating

`cube_dump_now.fleet_dump_now` now polls these keys first, picks
`min(newest_event_specnum_start)` across the 8 halves (= the
laggard's leading edge, so every faster half also has the cube),
subtracts `DEFAULT_LOOKBACK_CUBES = 4` × `t_det × sample_period_specnum`
to land inside every ring's `[oldest, newest)` retention window,
and uses *that* as the synthetic `event_specnum`. The legacy
corr_fast path is retained as a fallback so a partially-deployed
fleet still has *some* auto-arm signal, with a clear `WARNING` log
line and an `arm_info["search_ring_attempt"]` diagnostic
sub-dictionary so the operator can see why we fell back.

Wiring is one-line in `search_compute.SearchService.__init__`
(construct the publisher with `search_node_id` / `gpu_half` from
the service config) and one block in `_log_cube_progress` (call
`publish_from_ring(self._cube_ring)` best-effort). The publisher
swallows etcd errors after the first WARN.

Coverage: `tests/test_search_ring_mon.py` (11 tests — key layout,
non-empty/empty ring payload, ring-snapshot exceptions, put_dict
exceptions, subsequent-failure quiet mode, concurrent publishes)
+ 9 new tests in `tests/test_cube_dump_now.py`
(`TestResolveEventSpecnumFromSearchRing`,
`TestFleetDumpNowPrefersSearchRing`).

### Bug 4: `cube_uploader` rsync from search nodes to h23 silently failed

**Symptom.** The search nodes successfully staged dumps under
`/home/ubuntu/data/c2/cube_dump/<event>/cube_sX_gY_<specnum>.npz`
(verified by `ls` on each node and an 855 MB sanity-pulled cube),
but the corresponding files never appeared on h23's
`/dataz/dsa110/candidates/<event>/cubes/`.

**Root cause.** Two stacked issues:

1. `configs/dsart_search_rt.yaml::c1.uploader.remote_root` was set
   to `ubuntu@lxd110h23:/dataz/dsa110/candidates` — a bare
   hostname, which the search nodes can't resolve. Now corrected
   to `ubuntu@lxd110h23.pro.pvt:/dataz/dsa110/candidates`.
2. None of the search nodes had outbound SSH private keys, and
   none of their public keys were in h23's `authorized_keys`.

**Fix.**

```bash
# On h23 (this conversation): for each of n01 n02 n09 n13
ssh n0X.pro.pvt 'ssh-keygen -t ed25519 -N "" -f ~/.ssh/id_ed25519'
# Append each pubkey to ~/.ssh/authorized_keys on h23
# Prime ~/.ssh/known_hosts on each search node:
ssh n0X.pro.pvt 'ssh-keyscan -t ed25519,rsa lxd110h23.pro.pvt >> ~/.ssh/known_hosts'
# Smoke-test rsync — all 4 nodes pushed a 58 B tempfile successfully.
```

The smoke test was deliberately confined to `/tmp` and cleaned
afterwards. The 4 search-node pubkeys are now in h23's
`~/.ssh/authorized_keys` (backed up to
`~/.ssh/authorized_keys.bak_*`) and tagged with a
`# === cube_uploader keys from search nodes ===` comment so
future operators can locate / rotate them.
