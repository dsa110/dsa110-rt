## 2. `corr_fast` (MODIFIED routine, not a new unit)

The existing `corr_fast` python routine (`dsart.services.corr_fast_integration`)
was extended in two places. It is still launched under `dsart_rt.service`
on each corr node — there is no new systemd unit.

### 2.1 What changed

1. **CLI tuning knobs** for the production `RFIFlagger`. Now operators
   can re-tune the flagger by editing `configs/dsart_pipeline_rt.yaml`
   and pushing to etcd, no code change. The new CLI args:

   | flag | default | meaning |
   | --- | --- | --- |
   | `--sk-far`            | `1e-4` | SK chi-squared false-alarm rate |
   | `--bandpass-k`        | `5.0`  | MAD threshold for per-channel bandpass outliers |
   | `--group-k`           | `5.0`  | MAD threshold for whole-antenna outliers |
   | `--sumthr-max-m`      | `8`    | largest window in SumThreshold cascade |
   | `--sumthr-eta`        | `1.5`  | SumThreshold scale parameter |
   | `--sumthr-disabled`   | off    | (flag) disable SumThreshold entirely |
   | `--rfi-m-values`      | `64,256,1024,4096` | SK aggregation factors |
   | `--rfi-warmup-cubes`  | `2`    | cubes excluded from publish during warmup |

2. **RFI window aggregator + shm writer**. When `--rfi-mon-cn-id N` is
   passed, `corr_fast` accumulates a 16-cube window of `(autos.S1_4096,
   mask, source_tags)` on the GPU and serialises one
   record per window into `/dev/shm/dsart-rfi-window-<cn>` (POSIX-shm
   ring with seqlock torn-write detection). The mon CLI args:

   | flag | default | meaning |
   | --- | --- | --- |
   | `--rfi-mon-cn-id N` | – | required to enable the monitor; should equal `cn_id` |
   | `--rfi-mon-window-size`     | `16` | cubes per window (≈2.147 s @ production cadence) |
   | `--rfi-mon-freq-downsample` | `4`  | freq downsample factor for the published arrays |
   | `--rfi-mon-shm-slots`       | `64` | ring depth in shm (~137 s of history) |

### 2.2 Where the new args are pinned

`configs/dsart_pipeline_rt.yaml::routines.corr_fast.args`. After edit:

```bash
python3 tools/ops/push_dsart_to_etcd.py --instance all
# then on each corr node:  systemctl --user restart dsart-rt   (or send
# a `start` verb — the orchestrator re-reads /cnf on routine restart).
```

### 2.3 Health check

Same as before (alive routine in `/mon/corr_rt/<cn>.routines.corr_fast`)
plus the NEW per-block stderr lines now include a `flag_frac=` summary.

## 3. `rfi_monitor_export` (NEW routine on each corr node)

Python sidecar (`dsart.services.rfi_monitor_export`) that reads the
shm `corr_fast` writes into and republishes the data two ways. Runs
as a sibling routine under `dsart_rt` — no separate unit file.

### 3.1 Routine definition

In `configs/dsart_pipeline_rt.yaml`:

```yaml
- name: rfi_monitor_export
  cmd: python
  args: >-
    -u -m dsart.services.rfi_monitor_export
    --cn-id CN
    --etcd-cadence-s 2.0
    --staleness-s 10.0
    --http-bind 0.0.0.0
    --http-port 5780
    --log-level INFO
```

Where `CN` is the dsart_rt substitution placeholder for `cn_id`.

### 3.2 CLI arguments

| flag | default | meaning |
| --- | --- | --- |
| `--cn-id N`         | (required) | corr-node id; must match the producer's `--rfi-mon-cn-id` |
| `--etcd-cadence-s`  | `2.0` | how often to PUT `/mon/corr_rt/<cn>/rfi` |
| `--staleness-s`     | `10.0` | mark `degraded=true` if no new shm record in this window |
| `--http-bind`       | `0.0.0.0` | HTTP listen address |
| `--http-port`       | `5780` | HTTP listen port |
| `--log-level`       | `INFO` | python logging level |

### 3.3 Outputs

**Etcd**: `/mon/corr_rt/<cn>/rfi`, every 2 s, ~1.5 KB JSON dict. Full
schema in [`M7.6-MONITOR-POINTS.md`](./M7.6-MONITOR-POINTS.md) §4.

**HTTP** on port 5780 (loopback safe; default binds 0.0.0.0):

| endpoint | response |
| --- | --- |
| `GET /api/health`  | `{ok, cn_id, publish_seq, latest_age_s, staleness_threshold_s, uptime_s}` |
| `GET /api/meta`    | `{available, schema_version, cn_id, n_slots, n_ants, n_chan_ds, n_pol, window_size, freq_downsample, startup_utc_ns, host}` |
| `GET /api/latest`  | one window record, with `s1_full_mean`, `mask_count_*` arrays base64-encoded |
| `GET /api/recent?n=N` | last `N` records (defaults to ring depth, ~64 ≈ 137 s) |

The h23 `dsa_monitor.service` consumes `/api/recent` on startup
(backfill) and `/api/latest` every ~2 s thereafter.

### 3.4 Health check

```bash
# From any host with route to the corr nodes:
for h in n03 n04 n05 n06 n07 n08 n10 n11 n12 n14 n15 n16 n18 n19 n21 n22; do
  curl -sS --max-time 3 http://${h}.pro.pvt:5780/api/health \
    | python3 -c "import sys,json;d=json.load(sys.stdin);
print(f\"{'OK' if d['ok'] else 'BAD'}  cn={d['cn_id']:>3}  seq={d['publish_seq']:>5}  age={d['latest_age_s']:5.2f}s\")"
done
```

Expected: 16 lines of `OK cn=NN seq=NNNN age=0.x s` (age should be
< 2.2 s in steady state).

## 5. `dsart_rt_to_influx.service` (NEW; h20, system unit)

Python pusher (`tools/dashboard/dsart_rt_to_influx/pusher.py`) that
polls the etcd `/mon/{corr_rt,search_rt,service/*}/...` prefixes once
per second, dedupes on `mod_revision`, builds InfluxDB 1.x line
protocol points, and POSTs them to `localhost:8086`. Author: separate
sub-agent. Full local README at
[`tools/dashboard/dsart_rt_to_influx/README.md`](../../tools/dashboard/dsart_rt_to_influx/README.md).

### 5.1 Why on h20

Co-located with the long-running `influxd 1.7` daemon so writes go
loopback — same pattern as the legacy `etcd2db.service` and
`etcdWx.service`. The two services own disjoint etcd key spaces (the
legacy bridge owns `/mon/{ant,beb,cal,wx,corr,status,T1,T2,nsfrb*}/`;
this one owns `/mon/{corr_rt,search_rt,service/{corr,search}_rt}/`).
No overlap, no race.

### 5.2 Unit file

`tools/dashboard/dsart_rt_to_influx/dsart_rt_to_influx.service` (system
unit, not user). Deploy as root:

```bash
sudo cp tools/dashboard/dsart_rt_to_influx/dsart_rt_to_influx.service \
    /etc/systemd/system/
sudo cp tools/dashboard/dsart_rt_to_influx/startDsartRtToInflux \
    /home/ubuntu/bin/
sudo chmod +x /home/ubuntu/bin/startDsartRtToInflux
sudo systemctl daemon-reload
sudo systemctl enable --now dsart_rt_to_influx.service
```

The wrapper runs in the `casa38` env on h20 (already has `dsautils`,
`requests`, `influxdb`). The unit declares `Requires=influxdb.service`
so it starts after `influxd`.

Override per-host via `/etc/systemd/system/dsart_rt_to_influx.service.d/override.conf`.

### 5.4 Measurements written

| measurement | rows / tick | tag keys |
| --- | --- | --- |
| `corr_rt_routine`   | 8 / cn (128) | `cn_id, host, instance, state, routine` |
| `corr_rt_buffer`    | 0 / cn currently (would be ≤4 / cn) | `cn_id, host, buffer` |
| `corr_rt_capture`   | 1 / cn-port (32) | `cn_id, host, udp_port, control_port, arm_state` |
| `corr_rt_rfi`       | 3 / cn (48, per-pol fan-out) | `cn_id, host, pol` |
| `corr_rt_heartbeat` | 1 / cn (16) | `cn_id, host, state` |
| `search_rt_routine`   | 3 / cn (12) | `cn_id, host, instance, state, routine` + `coarse_dm` on the two compute halves |
| `search_rt_heartbeat` | 1 / cn (4) | `cn_id, host, state` |

Steady-state per **publish cycle** (every 2 s): ~240 rows. At the
default 1 s poll cadence + mod_revision dedup, roughly half of all
ticks emit 0 rows. The pusher's per-tick INFO log line is:

```
tick N: keys=K skipped=S built=B written=W capture_state_size=32
```

(`capture_state_size` should stay at 32 = 16 cn × 2 UDP ports.)

### 5.5 Cumulative-counter delta tracking

Every `corr_rt_capture` row emits **both** the raw cumulative counter
(`n_recv_packets` etc.) **and** a pre-diffed `n_<field>_delta` field.
The delta state is keyed on `(cn_id, udp_port)` and reset on `pid`
flip (capture binary restart) or any non-monotonic dip — so the
delta time series never shows a negative spike. Pusher details in
[`README`](../../tools/dashboard/dsart_rt_to_influx/README.md#cumulative-counter-delta-tracking).

### 5.6 Schema versioning

`SUPPORTED_SCHEMA_VERSION = 1`. The pusher refuses to ingest
`corr_rt_capture` / `corr_rt_rfi` payloads with a different
`schema_version` — bump the constant when a publisher bumps its
schema and update the corresponding `make_*_points` helper. Policy
in [`M7.6-MONITOR-POINTS.md`](./M7.6-MONITOR-POINTS.md) §8.

### 5.9 Planned-but-not-yet-published keys

The pusher's key-regex matcher anticipates the three planned

[`M7.6-MONITOR-POINTS-SEARCH.md`](./M7.6-MONITOR-POINTS-SEARCH.md) §7

## 8. Where to add the next new monitor service

Pattern to follow for any future addition to the `/mon/{corr,search}_rt/*`
control plane:

1. **Producer**: write to either etcd directly (small scalar dict, ~2 KB)
   OR a per-node POSIX shm if the volume is too high for etcd (e.g. the
   M7.6 RFI windows are ~30 KB per record).
2. If using shm, add a sidecar that reads it and publishes both
   etcd scalars (for cheap alerting) AND an HTTP endpoint (for raw
   arrays). The sidecar should be a sibling `routine` under
   `dsart_rt.service`, NOT a separate systemd unit.
3. Document the new etcd key shape in
   [`M7.6-MONITOR-POINTS.md`](./M7.6-MONITOR-POINTS.md) (corr side) or
   [`M7.6-MONITOR-POINTS-SEARCH.md`](./M7.6-MONITOR-POINTS-SEARCH.md)
   (search side). Carry a `schema_version` field.
4. Add a `make_*_points` helper + route in
   `tools/dashboard/dsart_rt_to_influx/pusher.py`. Wire it from
   `InfluxPusherService._route`. Bump `SUPPORTED_SCHEMA_VERSION` if
   the schema isn't `1`.
5. Add a Grafana panel in `build_dashboard.py`; regenerate the JSON
   snapshot; commit; re-POST.
6. If the data has a per-antenna or per-cube spatial structure that
   benefits from server-side plotting, add a renderer + route to
   `dsa_monitor` on h23 too.
