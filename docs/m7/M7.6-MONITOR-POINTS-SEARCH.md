# `/mon/search_rt/...` monitor-point schema reference

Author: realtime / search-node task M7.6 (May 2026)

Companion to [`M7.6-MONITOR-POINTS.md`](./M7.6-MONITOR-POINTS.md) (corr_rt
side). Conventions, schema-version policy, and the InfluxDB pusher
design overview live there; this document specifies only the
search_rt-specific deltas.

The phase-B fleet has **4 search nodes**: `cn_id ∈ {1, 2, 9, 13}`, hosts
`n01.pro.pvt`, `n02.pro.pvt`, `n09.pro.pvt`, `n13.pro.pvt`. Each search
node owns one pair of the 8 coarse-DM trials produced by the M4a transport
fan-out (see [§4](#4-search-fleet-topology)).

Two key shapes live under the search-side mon namespaces, both written
by the same `dsart_rt` orchestrator binary that publishes the corr-side
rollups:

| key | cardinality | cadence | publisher | section |
| --- | --- | --- | --- | --- |
| `/mon/search_rt/<cn>` | 1 per search node (4) | 2 s | `dsart.services.dsart_rt.RtOrchestrator._publish_mon_dict` | [§2](#2-monsearch_rtcn--routine-rollup) |
| `/mon/service/search_rt/<cn>` | 1 per search node (4) | 2 s, lock-free | `RtOrchestrator._publish_heartbeat` | [§3](#3-monservicesearch_rtcn--heartbeat) |

There are **no** per-routine sub-keys on the search side today (no
`/mon/search_rt/<cn>/rx/...`, no `/mon/search_rt/<cn>/compute/<half>/...`).
The `search_rx` and `search_compute` services log throughput / drop /
cube-cadence stats to stderr only; their structured-mon counterpart
is on the roadmap ([§7](#7-roadmap--mon-keys-that-do-not-exist-yet)).

---

## 1. Differences from the corr_rt schema

The orchestrator code path is shared (one binary, two instances), so
the rollup schema is **byte-for-byte identical** to corr_rt §2 except
for three populated fields and one absence:

| field | corr_rt value | search_rt value |
| --- | --- | --- |
| `instance` | `"pipeline_rt"` | `"search_rt"` |
| `cn` | one of 16: `{3..22} \ {9, 13, 17, 20}` | one of 4: `{1, 2, 9, 13}` |
| `host` | `lxd110h<cn:02d>` | `lxd110h<cn:02d>` |
| `routines` | 8 named children | 3 named children (`search_rx`, `search_compute_0`, `search_compute_1`) — see §2.2 |
| `buffers` | `{dada, eada, fada, bada}` with `metric: {}` | **always empty `{}` by design** — search nodes use POSIX-shm rings, not PSRDADA |

The `buffers: {}` is intentional: the M4a transport contract has
search nodes attaching to a single `/dsart-rxring-<cn>` POSIX-shm
SPMC ring created by `search_rx` itself (see
`configs/dsart_search_rt.yaml` lines 5–10 + 22). dsart_rt's
`dada_db` setup is unused on the search side, so the orchestrator
correctly publishes an empty `buffers` dict — pushers should not
emit `corr_rt_buffer` / `search_rt_buffer` points for search nodes.

The heartbeat schema is identical (3 fields). The same alerting rules apply.

For any field not called out below, treat it the same as corr_rt §2 / §5.

## 2. `/mon/search_rt/<cn>` — routine rollup

Per-node summary of which child processes (search_rt routines) are
alive. Published by the dsart_rt orchestrator on each search node once
per `mon_cadence_s` (default 2 s). Skipped for the cycle if a verb is
mid-flight; the heartbeat (§3) is the canonical "is the orchestrator
alive" signal.

### 2.1 Payload schema

Identical to corr_rt §2.1. For completeness:

| field | type | tag/field | meaning |
| --- | --- | --- | --- |
| `cadence` | float (s) | field | mon-publish cadence (= 2.0). |
| `time_mjd` | float | field | MJD timestamp at publish. Convert to unix via `(mjd - 40587) * 86400`. |
| `instance` | str | tag | Always `"search_rt"` here. |
| `cn` | int | tag | cn_id (1, 2, 9, or 13). |
| `host` | str | tag | publisher FQDN (`lxd110h01` etc.). |
| `state` | str | tag | orchestrator FSM state; steady state `"running"`. |
| `uptime_s` | float | field | seconds since `running` first entered. |
| `routines` | `dict[str, {pid:int, alive:bool}]` | nested | per-child process status (§2.2). |
| `buffers` | `{}` | nested | always empty for search_rt by design. |
| `last_verb` | `{verb:str, val:int|str|null, age_s:float} \| null` | nested | last verb received (`start` / `stop` / `reset`). `null` if never observed. |

### 2.2 `routines` sub-dict — three named children

Each value is `{"pid": <int>, "alive": <bool>}` (same shape as corr_rt).

| routine name | language | what it does | normal cadence |
| --- | --- | --- | --- |
| `search_rx` | py (`-m dsart.services.search_rx`) | C-epoll UDP fan-in. Binds 16 ports (6625..6640, one per corr chgroup) on the search node's `nic.search` address, reassembles fragmented prod_frames, publishes reassembled cube slots into `/dsart-rxring-<cn>` (POSIX-shm SPMC ring). | streams; cube cadence ~7.45/s |
| `search_compute_0` | py (`-m dsart.services.search_compute`) | GPU half 0 (physical GPU 0 via `CUDA_VISIBLE_DEVICES=0`). Attaches read-only to `/dsart-rxring-<cn>`, runs the M6 imager + detector on its owned pair of coarse-DM trials. | one cube every ~134 ms |
| `search_compute_1` | py (`-m dsart.services.search_compute`) | GPU half 1 (physical GPU 1 via `CUDA_VISIBLE_DEVICES=1`). Same attach + same compute, disjoint coarse-DM owner pair. | one cube every ~134 ms |

`alive == false` on any of the three is a **page-grade alert**: the
compute halves cannot resume mid-cube without losing the shm ring
attach, and `search_rx` going down silently drops the inbound UDP fan-in
without the corr senders noticing.

### 2.3 `buffers` sub-dict

Always `{}`. No PSRDADA on the search side. Pushers should emit no
points for this field.

### 2.4 `last_verb` sub-dict

Identical shape to corr_rt §2.4. Observed values on the live fleet:

| verb | val | meaning |
| --- | --- | --- |
| `start` | `null` | bring up the 3 routines; per-routine `alive=true` should follow within ~5 s |
| `stop` | `null` | SIGTERM the 3 routines; `alive` flips to `false` |
| `reset` | `null` | stop + restart |

Unlike corr_rt, search_rt has **no** `utc_start` / `utc_stop` verbs —
the search-side pipeline doesn't need wire-level arming because the
M4a transport TX side (corr nodes) inserts timestamps in every prod_frame.

### 2.5 Worked example (steady state, n01, May 2026)

```json
{
  "cadence": 2.0,
  "time_mjd": 61181.92571291506,
  "instance": "search_rt",
  "cn": 1,
  "host": "lxd110h01",
  "state": "running",
  "uptime_s": 11753.431,
  "routines": {
    "search_rx":        {"pid": 29689, "alive": true},
    "search_compute_0": {"pid": 29690, "alive": true},
    "search_compute_1": {"pid": 29691, "alive": true}
  },
  "buffers": {},
  "last_verb": {"verb": "start", "val": null, "age_s": 11753.441}
}
```

## 3. `/mon/service/search_rt/<cn>` — heartbeat

Lock-free 3-field heartbeat. Same shape and semantics as the corr_rt
heartbeat (corr doc §5). Use this as the single source of truth for
"is the search-rt orchestrator on this cn alive."

| field | type | tag/field | meaning |
| --- | --- | --- | --- |
| `cadence` | float (s) | field | `mon_cadence_s` (= 2.0). |
| `time_mjd` | float | field | MJD timestamp at publish. |
| `state` | str | tag | enum: `running` / `idle` / `starting` / `stopping` / `stopped` / `error`. |

Alert threshold: `now - mjd_to_unix(time_mjd) > 8 s` per cn.

```json
{"cadence": 2.0, "time_mjd": 61181.925712797325, "state": "running"}
```

## 4. Search-fleet topology

The 8 coarse-DM trials produced by the M4a transport fan-out are
sharded across the 4 search nodes, with each node owning a pair (one
per GPU half). The assignment is pinned by the per-host overrides in
`configs/dsart_search_rt.yaml` (lines 87–104, 186–192, 241–247):

| host | cn_id | half 0 (physical GPU 0) | half 1 (physical GPU 1) |
| --- | --- | --- | --- |
| `n01.pro.pvt` | 1 | coarse_dm = 0 | coarse_dm = 1 |
| `n02.pro.pvt` | 2 | coarse_dm = 2 | coarse_dm = 3 |
| `n09.pro.pvt` | 9 | coarse_dm = 4 | coarse_dm = 5 |
| `n13.pro.pvt` | 13 | coarse_dm = 6 | coarse_dm = 7 |

Each search node binds 16 UDP ports (`6625..6640`) on its `nic.search`
address (`10.41.0.205`, `10.41.0.222`, `10.41.0.253`, `10.41.0.238`
respectively) and receives one prod_frame per coarse-DM per chgroup
per cube. At the production op-point (n_corr=16, n_coarse_dm=8,
cube cadence ~7.45 Hz, ~420 MiB per cube per coarse-DM × 2 owned =
~840 MiB/s per search node before fragmentation overhead).

Production op-point (per
`configs/dsart_search_rt.yaml::search_compute_{0,1}.args`):

| parameter | value | notes |
| --- | --- | --- |
| `n_grid` | 256 | imager grid |
| `n_fdm` | 34 | fine-DM rows per coarse-DM (= N_fine / 8 from the v2 plan) |
| `t_det` | 192 | detector cube length in samples |
| `cube_cadence_samples` | 128 | new samples per cube ⇒ overlap = 64 = b_max |
| `t_int_search_us` | 1048.576 | matches corr `t_int_fast` at 32× native |
| `fan_in_min_corrs` | 15 | accept cube if ≥ 15 of 16 corrs reported in |
| `n_active_dms_per_corr` | 2 | (M4a chunk 6) |
| `pipeline_overlap` | on | prefetch cube N+1 H2D while computing cube N |
| `device` (per half) | `cuda:0` (after `CUDA_VISIBLE_DEVICES` mask) | each half pinned to one physical GPU |

The 134.218 ms/cube real-time budget is therefore per (search node ×
GPU half), not per fleet. M7.2.8 verified ~105 ms p50 at the production
geometry with `--pipeline-overlap` enabled.

## 5. InfluxDB pusher design — search-side specifics

Reuse the framework from the corr_rt doc §6. Additional measurements:

| measurement | from | tag keys | timestamp |
| --- | --- | --- | --- |
| `search_rt_routine` | §2 `/mon/search_rt/<cn>`, expanded by routine | `cn_id`, `host`, `instance`, `state`, `routine` | `mjd_to_unix(time_mjd)` |
| `search_rt_heartbeat` | §3 `/mon/service/search_rt/<cn>` | `cn_id`, `host`, `state` | `mjd_to_unix(time_mjd)` |

For the routine expansion, emit one point per (cn_id, routine_name):

```
measurement: search_rt_routine
tags:        cn_id="1" host="lxd110h01" instance="search_rt"
             state="running" routine="search_compute_0"
fields:      pid=29690i alive=1i uptime_s=11753.431
             last_verb_age_s=11753.441 (parent-level field, duplicated to each row)
time:        mjd_to_unix(time_mjd)
```

Then "alive routines per search node" is one Grafana query:
`SELECT count_if(alive==1) WHERE instance='search_rt' GROUP BY cn_id`
— should always equal 3 in steady state.

### 5.1 Skip the buffer expansion on search-rt

Unlike corr_rt, **do not emit `search_rt_buffer` points**: `buffers` is
always `{}`. Including the empty dict would just add noise. Detect on
`instance == "search_rt"` in the pusher and skip the buffer-fan-out
code path.

### 5.2 Coarse-DM owner tagging

Static metadata: derive the half→coarse_dm mapping from cn_id once at
pusher startup (it doesn't change without a config push + restart) and
tag every `search_compute_{0,1}` routine point with its owned
`coarse_dm` (= `{1:0|1, 2:2|3, 9:4|5, 13:6|7}[cn_id][half]`):

```python
COARSE_DM_OWNER = {
    (1, 0): 0, (1, 1): 1,
    (2, 0): 2, (2, 1): 3,
    (9, 0): 4, (9, 1): 5,
    (13, 0): 6, (13, 1): 7,
}
```

This lets Grafana queries like "show me the alive-history of every
coarse-DM trial across the fleet" work with a single query against
`search_rt_routine`. Bake the mapping into the pusher; do not query
the running services for it.

### 5.3 Alert thresholds (search-side additions)

| condition | severity |
| --- | --- |
| any search `routines.search_rx.alive == 0` for > 10 s | **page (fleet-down)** — fan-in stops; corr senders will start dropping next cube |
| any search `routines.search_compute_{0,1}.alive == 0` for > 10 s | page — coarse_dm owner is dead, that DM trial is dark fleet-wide |
| `/mon/service/search_rt/<cn>.time_mjd` stale > 8 s | page — orchestrator wedged |
| count of alive `search_compute_*` across fleet < 8 for > 5 s | page — at least one coarse-DM owner is missing |
| `/mon/search_rt/<cn>.buffers != {}` | warn — config drift; only corr_rt should have non-empty buffers |

### 5.4 Cadence and polling

Polling cadence: same as corr_rt (1 s tick, polls the `/mon/search_rt/`
+ `/mon/service/search_rt/` prefixes). 4 keys per prefix = 8 records per
tick; trivial overhead.

There are no cumulative-counter fields in either search-side key, so
the `pid`-flip reset machinery from corr_rt §6.3 isn't needed here.

## 6. Verification snippets

```bash
# (1) enumerate everything under /mon/search_rt/
python3 -c "from dsautils.dsa_store import DsaStore;
c=DsaStore().get_etcd();
[print(m.key.decode()) for _, m in c.get_prefix('/mon/search_rt/')]"

# (2) confirm all 4 search nodes alive with 3 routines each
python3 -c "
import json; from dsautils.dsa_store import DsaStore; s=DsaStore()
for cn in (1, 2, 9, 13):
    d = s.get_dict(f'/mon/search_rt/{cn}') or {}
    routs = d.get('routines') or {}
    alive = sum(1 for r in routs.values() if r.get('alive'))
    print(f'cn={cn:2d}  state={d.get(\"state\",\"?\"):8s}  routines={alive}/{len(routs)}')
"

# (3) confirm heartbeat freshness fleet-wide
python3 -c "
import time, json; from dsautils.dsa_store import DsaStore; s=DsaStore()
for cn in (1, 2, 9, 13):
    d = s.get_dict(f'/mon/service/search_rt/{cn}') or {}
    age = time.time() - (d['time_mjd'] - 40587) * 86400 if d else float('inf')
    print(f'cn={cn:2d}  hb_age={age:5.1f}s  state={d.get(\"state\",\"?\")}')
"
```

## 7. Roadmap — mon keys that do not exist yet

These are the structured monitoring keys the search-rt pusher will
eventually want to ingest. They are **not** yet written by any service
in the current `dsa110-rt` tree — flagged here so the InfluxDB pusher's
key-regex matcher can be designed once and extended later without a
schema-version bump on the existing keys.

### 7.1 `/mon/search_rt/<cn>/rx` (planned)

Per-node RX fan-in counters analogous to `/mon/corr_rt/<cn>/capture/<port>`,
aggregated across the 16 UDP ports `search_rx` listens on. Expected
fields (preview, **not normative**):

```
schema_version, cn_id, n_ports, port_base,
n_recv_frames_total, n_recv_bytes_total,
n_reassembled_cubes, n_dropped_frames, n_dropped_cubes,
n_pattern_id_mismatch, n_corr_under_min,
ring_n_filled, ring_n_dropped_owner, ring_n_dropped_consumer,
arm_state, age_ms, degraded, publish_unix
```

Would be published by `search_rx` itself (analogous to how
`capture_control` proxies the C capture binary's shm into etcd —
except `search_rx` is already python, so no shm bridge needed; it
can call `DsaStore.put_dict` from its own status loop).

### 7.2 `/mon/search_rt/<cn>/compute/<half>` (planned)

Per-(search-node, GPU-half) cube-cadence + budget tracking. Expected
fields:

```
schema_version, cn_id, half, coarse_dm_owners (list of ints),
n_cubes_processed, n_cubes_dropped, n_cubes_in_flight,
last_cube_wall_ms, last_cube_imager_ms, last_cube_detector_ms,
p50_cube_wall_ms_window60s, p99_cube_wall_ms_window60s,
device, image_backend,
arm_state, age_ms, degraded, publish_unix
```

This is the search-side analog of the corr-side per-cube budget tracker
that already prints to stderr (`per_block_ms` in
`corr_fast_integration.py`). Lifting it into etcd would let Grafana
plot the 134.218 ms RT budget alongside per-cube wall on every search
node.

### 7.3 `/mon/search_rt/<cn>/cands` (planned, M7.x)

When the M6 candidate clusterer + cube_dump + cands_logger are turned
on (gated off for M7.2; turned on for M7.3+), an analogous per-node
candidate-throughput key is the natural place to expose:
trigger rate, last-trigger UTC, cube-dump backlog, cands_logger queue
depth, etc. Out of scope for this document.

### 7.4 Pusher implication

The InfluxDB pusher's key-prefix matcher (see corr_rt doc §6.7
reference outline) should anticipate these. Suggested regexes:

```python
KEY_SEARCH_CN       = re.compile(r"^/mon/search_rt/(\d+)$")
KEY_SEARCH_HEARTBEAT= re.compile(r"^/mon/service/search_rt/(\d+)$")
# planned, currently match nothing but defined so they're ready:
KEY_SEARCH_RX       = re.compile(r"^/mon/search_rt/(\d+)/rx$")
KEY_SEARCH_COMPUTE  = re.compile(r"^/mon/search_rt/(\d+)/compute/(\d+)$")
KEY_SEARCH_CANDS    = re.compile(r"^/mon/search_rt/(\d+)/cands$")
```

Wire the planned matchers to `make_*_points` helpers that raise
`NotImplementedError` until the underlying publishers land; that way
the pusher fails loudly the day someone deploys a new publisher
without updating the pusher, instead of silently dropping points.

## 8. Schema-version policy

Same as corr_rt §8: the rollup and heartbeat keys do not carry a
`schema_version` field, and the policy is "additive only — anything
breaking requires a new key shape". The planned per-routine keys
(§7) will carry `schema_version: 1` from day one, in line with the
corr_rt capture / rfi keys.
