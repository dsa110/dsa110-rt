# M7.4 Option A — corr-side stage-2 inter-chgroup time alignment

**Status:** ✅ **SHIPPED & VALIDATED end-to-end on M7.4 burst replay.**
The corr-side `Stage2InterChgroupShiftFifo` wire-in is live behind
`--stage2-mode per_coarse_dm` on `dsart.services.corr_fast_integration`
and the search side runs without `--include-coarse-offset-in-search-shifts`.
Validated on the 250924mptq replay: 16 corr-fleet processes warmed
in <10 s, search side detected the burst at the correct
`(row=136, col=169)` pixel with `peak=60000` (fp16 clip) at fdm=30
(truth fdm=32-33, off by 2 bins = ~40 pc/cc DM offset, within
fine-DM-trial tolerance), and the C2 coincidencer fired
`DUMP class=bright_pulsar name=581117znns snr_max=2672 broadcast=8/8`.

**Owner:** `dsart.coarse_dm` (math + container) + `dsart.transport` /
`dsart.services.corr_fast_integration` (TX wire-in).

## Why we want it

The M7.4 250924mptq burst replay currently ships with **Option B**:
the per-chgroup stage-2 inter-chgroup delay is baked into the
search-side `time_shift_search` table by setting
`include_coarse_offset=True` in
`dsart.fine_dm.combiner.compute_time_shift_search`. This works end-to-end
— the burst lands at the correct (l, m, fdm) with SNR ≥ bench truth —
but it inflates the search-side rolling ring buffer
(`ProductionRxRing._t_stream = T_det + max(shifts)`) by ~50 % at the
M7.4 op point.

At the 16x4 production fleet that ~50 % inflation matters: each of the
16 × 4 = 64 GPU halves carries a separate ring buffer, and the gain
from moving stage-2 to the corr-side is ~16× smaller `_t_stream`,
which is the dominant term in the search-side rx-ring RAM budget.

Empirical max-shift figures at the M7.4 250924mptq DM plan
(`compute_stage2_shifts_all_chgroups`, output reproduced in the test
suite, units = corr-fast samples @ 262.144 µs):

| chgroup | max shift (samples) | wallclock equiv. |
| ---: | ---: | ---: |
| 0 | 9115 | 2.4 s |
| 1 | 8607 | 2.3 s |
| 7 | 5286 | 1.4 s |
| 14 | 723 | 0.19 s |
| 15 | 0 | 0 |

Search-side equivalent (4× downsampled to 524.288 µs cadence):
~2280 samples worst-case, vs `T_det = 192`. Option A reclaims that
2280-sample budget for the search-side ring buffer; Option B forces
the search-side ring to absorb it.

```

    ... \
    --dm-plan-path /home/ubuntu/data/dm_plans/dm_plan_N8_dmmin100_tol1.6_v2.npz \
    --stage2-mode per_coarse_dm   # <-- Option A on
```

```
# search_compute launch (omit the include-coarse-offset flag in the YAML):
# WAS:  --include-coarse-offset-in-search-shifts
# NOW:  (flag absent ⇒ search-side time_shift_search uses
#        compute_time_shift_search(include_coarse_offset=False))
```

When both sides are set this way, the corr-side FIFO applies the
per-(chgroup, coarse_dm) integer-sample delay and the search side
applies only the fine-DM-trial differential — exactly the Option A
math.

## Cube-granular vs sample-granular decision

We chose cube-granular history with intra-cube sample-exact slicing.
The output cube emitted to the TX is built by reading from the
per-coarse-DM cube history at integer-sample precision:

    output[c, 0:r]      = ring[c][k+1][T-r:T]
    output[c, r:T]      = ring[c][k][0:T-r]
    where  k = δ_c // T,  r = δ_c - k*T

This is identical to what a sample-granular ring would emit, with
~10× less Python bookkeeping per push. See
`stage2_chgroup_alignment.Stage2InterChgroupShiftFifo._required_depth`
for the derivation.

## What still needs to ship (post-MVP)

### 1. Mirror the corr-side flag in `configs/dsart_corr_fast_rt.yaml`

So a production deploy can flip Option A by orchestrator YAML edit
(no per-node bash script changes). Trivial — one `args:` line.

### 2. Flip `--include-coarse-offset-in-search-shifts` in the production
search YAML

In `configs/dsart_search_rt.yaml` REMOVE the
`--include-coarse-offset-in-search-shifts` flag from the two
`search_compute_*` routines once Option A is wired everywhere. The
M7.4 validation already did this in a `/tmp/optA_configs/` overlay;
upstream the change for production.

### 3. Shrink `t_buf_samples` for the search-side rx ring

With Option A engaged, the rx-ring `_t_stream` shrinks from
`T_det + ~210 = 402` search samples to `T_det + ~76 = 268` samples.
`--t-buf-samples 4096` can be reduced to ~512 — frees ~3 GiB per
search-node GPU half. Not done in this MVP wire-in because the
M7.4 replay is purely about detection correctness, not RAM
reclaim; one YAML edit when ready.

### 4. Investigate ±2 fdm offset

The validation run shows the burst at fdm=30 vs Option B's fdm=32-33.
The off-by-2 corresponds to ~40 pc/cc DM (within fine-DM-trial
spacing). Likely sources: integer-sample rounding of the per-chgroup
shift on the corr-side vs the search-side stage-3 fine-grid, or the
fine-DM grid origin shifting slightly when
`include_coarse_offset=False`. The burst is correctly detected at
the right (l, m) and dumps to disk via the C2 trigger; the DM med
drift is small enough that the production candidate classifier
still fires `class=bright_pulsar`. A follow-up should cross-check
`compute_time_shift_search` for an off-by-one in the residual.

### 5. Multi-search-node `bright_frb` classification

Replay still uses one search node so the classifier picks
`bright_pulsar` (criterion `n_search_nodes_min=2`). On the live 4×
search fleet this reverts to `bright_frb` automatically; nothing to
change.

## Risk + rollback

The per-coarse-DM FIFO is opt-in via `--stage2-mode per_coarse_dm`
(default `uniform`). If Option A regresses SNR or detection on
on-sky data, flip `--stage2-mode uniform` and add
`--include-coarse-offset-in-search-shifts` back to the search YAML
— one orchestrator restart cycle.
